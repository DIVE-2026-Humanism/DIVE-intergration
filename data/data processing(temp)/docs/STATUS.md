```
KCB CSV → 전처리 → 파생변수 → 6유형 분류 → predictions.jsonl
```

### 접점: `predictions.jsonl` — 지금 스키마로는 연결 불가


## 3. 모델 레포 피드백 (우선순위순)

### 🔴 1인 추론 시 설명이 전부 망가진다 — `src/infer.py:75`

```python
percentile_ranks = {f: features[f].rank(pct=True, method="average") for f in MODEL_FEATURES}
```

퍼센타일을 **추론 배치 내 상대 순위**로 계산한다. 배치가 크면 맞지만
**셀프진단 데모는 1명 입력**이고, `n=1`이면 `rank(pct=True)`가 항상 `1.0` →
모든 근거가 "상위 20% 구간"으로 찍힌다. 연체 3건에 신용평점 300점인 사람에게도 그렇게 나온다.

→ `artifacts/quantiles.json`에 이미 전체 분위수를 저장하므로(`train.py:156`),
**저장된 분포 기준으로 퍼센타일을 매기면** 해결되고 배치 크기와도 무관해진다.

*(이 환경에 pandas가 없어 실행 검증은 못 함. `rank(method='average')`가 단일 원소에 1.0을
반환하고 `pct=True`가 개수로 나누는 동작에 근거한 판단.)*

### 🟠 유보 레코드가 스키마를 바꾼다

`판정: "유보"`면 `대분류`/`유형` 키가 **아예 없고** `모델참고분류`/`사유`가 대신 들어온다.
다운스트림에서 `record["유형"]`이 KeyError를 낸다. Thin Filer는 라이트 트랙의 주요 경로라 반드시 밟는다.
→ 키 집합은 고정하고 값을 `null`로 둘 것.

### 🟠 규칙 충돌 시 파이프라인이 죽는다 — `src/labeling.py:133`

규칙이 겹치면 `ValueError`로 전체가 중단된다. 개발 중 계약 검증으로는 옳지만
**대회 당일 실데이터에서 터지면 복구 시간이 없다.** 5행 샘플로는 절대 안 걸린다.
→ `--strict` 플래그로 분리하고 당일엔 경고 + `CLASS_ORDER` 우선순위 폴백으로.

### 🟡 단일 모델 통합의 부작용 — 경제안정성 점수가 갈 곳을 잃었다

> **전제**: 레포(2026-07-21)가 브리프(07-17)보다 최신이다. 브리프의 2모델 구성
> (모델1 지도학습 점수 + 모델2 비지도 클러스터링)은 **CatBoost 단일 다중분류로 통합**되었고,
> 6유형(V1~V3/S1~S3)도 확정 사항이다. 아래는 그 결정을 전제로 한 지적이다.

브리프에서 **경제안정성 점수 0~100은 모델1의 산출물**이었다. 모델1이 사라지면서
점수를 만들 주체가 없어졌고, README도 이를 인정한다
("현재 코드는 아직 확률과 점수를 출력하지 않는다").

게다가 README가 계획한 것은 점수의 성격이 다르다:

- 계획된 `유형 적합도 점수` = "당신은 S3형이 맞다(**확신도** 87%)"
- 필요한 `경제안정성 점수` = "당신의 경제 안정성은 **72점**"

전자는 분류가 얼마나 확실한지고, 후자는 얼마나 안정적인지다.

#### 둘은 비례하지 않는다 — U자 관계다

적합도는 "어느 유형인지 얼마나 확신하는가"인데, **가장 위험한 사람과 가장 안정적인 사람
양쪽 다 확신하기 쉽다.** 확신도가 낮은 쪽은 오히려 중간층이다.

| | 확률 분포 | 적합도 | P(취약) | 안정성 점수 |
|---|---|---|---|---|
| A 중증 연체자 | V1 0.90 / 나머지 0.10 | **90** | 0.98 | **2점** |
| B 무부채 건전 | S3 0.90 / 나머지 0.10 | **90** | 0.07 | **93점** |
| C 애매한 경계 | V3 0.35 / S1 0.33 / S2 0.32 | **35** | 0.35 | **65점** |

- A와 B는 **적합도가 똑같이 90점인데 상태는 정반대다.** 적합도로는 구분이 불가능하다.
- 적합도로 정렬하면 **A(90) > C(35)** 가 되어 "중증 연체자가 애매한 사람보다 안정적"이라는
  결론이 나온다. 화면이 거꾸로 뒤집힌다.

원인은 요약 방식이다. 같은 확률 벡터에서

- 적합도 = `max(p)` — 최댓값 하나만 봐서 **어느 쪽 극단인지 정보가 사라진다**
- P(취약) = `p[V1]+p[V2]+p[V3]` — **방향이 살아있다**

모델을 바꾸거나 재학습할 필요는 없다. `predict_proba`를 어떻게 요약하느냐의 차이다.

#### 적합도는 버리지 말고 신뢰도로 쓴다

적합도는 "이 진단을 얼마나 믿어도 되는지"로는 제대로 된 지표다.
브리프가 라이트 진단에 요구한 **신뢰구간 제시**가 정확히 이 자리다.

> **경제안정성 65점** · V3 소득·생활 취약형
> *(진단 신뢰도 보통 — 안정형과 경계에 있습니다)*

#### 실데이터로 확인하는 법

대회 당일 실데이터를 받으면 아래로 U자 관계를 눈으로 확인할 수 있다.
가정이 맞는지 검증하고, 발표 자료에도 그대로 쓸 수 있다.

```python
proba = model.predict_proba(X)                      # (n, 6)
classes = list(model.classes_)
v_idx = [classes.index(c) for c in ("V1", "V2", "V3")]

fit_score = proba.max(axis=1)                       # 유형 적합도
p_vuln    = proba[:, v_idx].sum(axis=1)             # 취약 확률
stability = 100 * (1 - p_vuln)                      # 경제안정성 점수

# 1) 산점도가 U자면 가정이 맞다 (양 끝 높음, 가운데 낮음)
#    x=stability, y=fit_score

# 2) 상관계수가 0 근처면 "비례하지 않는다"의 증거가 된다
import numpy as np
print("피어슨 상관:", np.corrcoef(stability, fit_score)[0, 1])

# 3) 안정성 상·하위 10%에서 적합도 평균이 비슷하면 U자 확정
lo, hi = np.percentile(stability, [10, 90])
print("하위10% 적합도:", fit_score[stability <= lo].mean())
print("상위10% 적합도:", fit_score[stability >= hi].mean())
```

**주의**: `predict_proba`는 캘리브레이션 전이면 과신(overconfidence) 경향이 있어
`stability`가 0/100 쪽으로 쏠릴 수 있다. README가 언급한 OOF 보정을 **`p_vuln`에**
적용한 뒤 점수화할 것.

이게 없으면 다음이 전부 안 돌아간다:
- 정책 추천 목록의 정렬 기준
- 또래 대비 비교 화면
- **예산 배분 시뮬레이터** (차별화 1순위)

**제안**: 단일 모델 구성을 유지한 채로 클래스 확률에서 유도할 수 있다.

```
P(취약) = P(V1) + P(V2) + P(V3)
경제안정성 점수 = 100 × (1 − P(취약))
```

모델 하나로 유형과 점수를 동시에 얻고, 취약 확률은 예산 시뮬레이터의
"연체 전환 감소" 추정에도 바로 쓰인다. `predict_proba`만 꺼내면 되고
캘리브레이션(README가 언급한 OOF 보정)은 이 확률에 적용하면 된다.

## 4. 요건 JSON 스키마 — 설계 방향 (미확정)

### 원칙 3가지

1. **출처를 물리적으로 분리한다** — `structured`(API 원본) / `extracted`(LLM) / `derived`(코드 계산).
   검수 대상이 `extracted`로 한정되고, 발표에서 "LLM이 만진 부분은 여기뿐"이라고 짚을 수 있다.
2. **"정보 없음"(`null`)과 "제한 없음"(`ANY`)을 구분한다.**
   이 구분이 가능/불가/정보부족 **3분류의 기반**이다. 뭉치면 3분류가 원리적으로 불가능해진다.
3. **요건마다 판정 주체를 명시한다** — `KCB`(데이터로 판정) / `USER`(물어봄) / `NEVER`(아무도 모름).
   원가구 소득 같은 건 `NEVER`로 박아두면 자동으로 "정보부족"이 된다.

### 부수 규칙

- `유형가중치`는 요건 **밖**에 둔다. 자격 판정에 쓰지 않고 정렬에만 쓴다.
  유형이 자격을 좌우하면 "모델이 판정한다"가 되어 브리프의 환각 통제 설계와 충돌한다.
- `혜택`을 숫자로 뽑아둔다(월 20만원 × 24개월). ④단계에서 LLM에 넘길 효과 수치가 된다.

### 판정 예시 — 25세 / 해운대구 / 연소득 2,650만원 / 무주택 / V3형

```
✅ 나이 25세 → 19~34 통과      ✅ 지역 26350 → 통과
✅ 무주택 → 통과                ✅ 본인소득 중위 60% 이하 → 통과
❓ 원가구 소득·재산 → 판정불가 (KCB에 정보 없음)
❓ 중복수혜 → 사용자 확인 필요

→ "정보부족" — 본인 조건은 모두 충족, 부모님 소득 확인 필요
```

"불가"가 아니라 **"본인 조건은 다 맞으니 이것만 확인하세요"**로 안내된다.
데이터 한계를 숨기지 않는 설계라 발표에서도 강점이 된다.

### a. 마감된 359건을 어떻게 할까

빼면 추천 풀이 107건(상시 69 + 진행중 38)으로 줄고, 넣으면 끝난 정책을 보여주게 된다.

> **제안**: 남기되 `상태: 마감`으로 표시하고 기본 숨김. 매년 반복 사업이 많아
> "작년에 이런 게 있었다"는 정보 가치가 있고, 데모 추천 개수도 확보된다.
> 단 `bizPrd`가 사업기간이라 진짜 종료와 올해 회차 종료를 구분해야 한다 — 미해결.

### b. 정책 하나에 지원 항목이 여러 개면

"부산 청년 신용회복 지원"은 상담(조건 없음) / 연체예방비용(소득 50만원 이상)으로 요건이 다르다.
항목별로 쪼개면 정확하지만 스키마가 복잡해진다.

> **제안**: 해커톤 범위에선 **가장 느슨한 요건으로 통합**하고 설명에서 언급.

### c. 534건 전부 vs 부산 한정 117건 — 어디까지 구조화할까

LLM 추출 + 사람 검수 비용이 여기서 정해진다.

> **제안**: 주거 43건 + 금융·복지 계열 + 부산 한정 117건 우선(중복 제외 150건 내외).
> 나머지는 정형 필드만으로 판정하고 `extracted`는 비워둔다.
