# DIVE 2026 · 부산 청년정책 매칭 — 데이터 파트

> 부산 청년의 신용·소비 데이터(KCB)와 청년정책을 이어, **받을 수 있는 정책을
> 정직하게 판정**하는 서비스. 이 저장소는 그중 **정책 데이터 수집·정제 파이프라인**과
> **도메인 분석**을 담당한다. 진단·분류·추천 런타임은 별도 AI 서버(`ai.beceleb.org`)가 맡는다.

최종 갱신: 2026-07-24

---

## 0. 한눈에

```
온통청년 API ──fetch──▶ raw(534) ──preprocess──▶ clean(175) ──export──▶ AI 서버 DB
                                    (마감필터+정규화)         (서버 스키마)
```

- **수집**: 온통청년 OpenAPI에서 부산 청년정책 **534건**
- **정제**: 마감 정책 제외 → **175건**, 요건 코드 디코드·정규화
- **핸드오프**: AI 서버 ingest용 스키마로 export
- **차별점**: 가능/불가만이 아닌 **"정보부족"까지 3분류** — 데이터 한계를 숨기지 않는다

## 2. 파이프라인 실행

```bash
# 인증키는 .env 에 (온통청년 마이페이지 > 오픈API 발급)
set -a; source .env; set +a

python3 src/fetch_policies.py       # 534건 수집 → raw
python3 src/preprocess.py           # 마감필터 534→175, 요건정규화 → clean
python3 src/export_policies.py       # 서버 스키마 export
```

> **마감은 실행일 기준으로 판정된다.** 시간이 지나면 결과가 바뀌므로,
> 대회 직전 위 3단계를 재실행해 서버에 재ingest하는 것이 갱신 루프다.

### preprocess의 두 스텝 (STEPS 리스트에 등록, 확장 가능)

1. **마감필터** — `aplyPrdSeCd=마감`(명시) + `종료일<오늘`(경과) 제외. 534 → 175
2. **요건정규화** — 각 정책에 `_norm` 부착: 상태·지역구분·대분류·요건(디코드)·llm추출필요

새 전처리는 `(records, ctx) → records` 함수 하나 쓰고 `STEPS`에 한 줄 추가하면 된다.
원본 60필드는 건드리지 않고 `_norm`에만 쌓는다.

## 3. 데이터로 확인한 것 (핵심 인사이트)

### 신뢰성 — 데이터를 실제로 열어야 아는 함정

| 발견 | 수치 | 함의 |
|---|---|---|
| **마감 정책이 다수** | 534 중 **359건(67%)** | 안 거르면 죽은 정책을 추천 |
| **소득요건이 정형필드에 없음** | `earnMinAmt` 유효 0건 | 자유서술에서 추출해야 함 |
| **"소득무관"인데 조건 숨음** | 14건+ | 코드값(`earnCndSeCd`)만 믿으면 오판 |
| **연령제한 플래그가 거짓말** | Y인데 나이값 있음 42건 | 플래그 버리고 min/max 값만 사용 |
| **코드가 콤마 다중값** | `jobCd` 등 | split + "제한없음"은 축마다 다른 코드 |

### 판정 가능성 — KCB × 정책의 경계

- 정책 요건축을 KCB로 채울 수 있는지 전수 대조 → **KCB로 판정 불가는 30%뿐**
- **핵심 도메인 주거 43건은 제약 0건**, 금융·복지도 9건뿐 → 노리는 영역은 거의 완전판정
- KCB에 없는 축(학력·혼인·특화)은 **라이트 진단 7문항이 메움** → 두 진단모드는 보완재

### 정직한 3분류 — 이 프로젝트의 차별점 ⭐

정책 판정을 **가능 / 불가 / 정보부족** 세 갈래로 나눈다.

```
25세 · 해운대 · 연소득 2,650만 · 무주택 · 재직자
  ✅ 나이 25 → 19~34 통과      ✅ 지역 해운대 통과
  ✅ 무주택 통과               ✅ 본인소득 중위 60% 이하 통과
  ❓ 원가구(부모) 소득·재산 → 판정불가 (KCB에 없음)
  ❓ 중복수혜 이력 → 사용자 확인 필요
  → "정보부족: 본인 조건은 다 맞으니 부모님 소득만 확인하세요"
```

"불가"로 뭉개지 않고 **"이것만 확인하세요"** 로 안내한다. 원가구 소득처럼 **아무도 모르는
축(NEVER)** 은 자동으로 정보부족이 된다. 데이터 한계를 드러내는 설계라 발표에서 강점이 된다.

## 4. AI 서버 연동

앱의 런타임(진단·분류·추천)은 AI 서버가 처리한다. 이 저장소는 **정책 데이터를 서버 DB에
공급**한다. 계약은 `meeting/idea/integration_guide.md` 및 `https://ai.beceleb.org/openapi.json`.

| 항목 | 값 |
|---|---|
| Base | `https://ai.beceleb.org` · `POST /v1/diagnose` |
| 모드 | `light`(7문항) / `precise`(7문항 + KCB 43필드) |
| 계약버전 | 1.2 |

**두 모드 모두 라이트 7문항을 사용**한다(idea 다이어그램). 정밀은 KCB가 연령·소득·지역을
선채움하고 사용자가 혼인·직업군·학력·특화를 보완한다.

### 확인 필요 (담당자와)

- 서버 정책 DB를 **내 export 175건으로 교체** 가능한지 (현재 서버는 동일 프로필에 15건만 반환)
- **자격판정에 "정보부족(확인필요)" 상태가 있는지** — 없으면 3분류 차별점을 넣자고 제안
- 소득요건 텍스트 추출을 **서버 ollama가 하는지** — 하면 `llm_extract.py` 불필요

## 5. 컴포넌트 상태

> 각 모듈이 무엇을 입력받아 어떤 처리를 하는지(필터 종류·축별 정규화·판정 로직)는
> **[`docs/MODULES.md`](docs/MODULES.md)** 에 함수 단위로 기술.


| 모듈 | 역할 | 상태 |
|---|---|---|
| `fetch_policies.py` | 온통청년 수집 | ✅ 데이터 파이프라인 (유효) |
| `preprocess.py` | 마감필터·요건정규화 | ✅ 데이터 파이프라인 (유효) |
| `export_policies.py` | 서버 스키마 export | ✅ 핸드오프 (유효) |
| `rules.py` | 자격판정 3분류 | 🔷 참조·검증용 (런타임은 서버) |
| `profile.py` | 입력→통합프로필 | 🔷 참조·검증용 (런타임은 서버) |
| `recommend.py` | 그룹핑·추천정렬 | 🔷 참조·검증용 (런타임은 서버) |
| `llm_extract.py` | 소득요건 추출 계약 | ❓ 서버 추출 여부에 따라 |
| 소비패턴 분석 | 또래대비 피드백 | ⬜ 서버가 소비피드백 제공 (중복 확인) |

> AI 서버 등장 전 `rules/profile/recommend`는 런타임 로직이었으나, 서버가 이를 수행하므로
> 지금은 **정책 데이터 검증 + 매칭 로직 레퍼런스**로 남긴다.

## 6. 남은 과제

- **정책 데이터 서버 이관** — export 스키마를 담당자와 확정 후 ingest
- **3분류 살리기** — 서버 자격판정에 "정보부족" 상태 반영 제안
- **소득요건 추출 분담** — 서버 LLM vs `llm_extract.py` 결정

### 막힌 것

- **KCB `직업군` 코드북 없음** — 420·910 등을 `jobCd` 라벨로 매핑 불가.
  라이트 폼 선택으로 우회되나, KCB 단독 판정에선 미해결. 발제사 Q&A 최우선.
- **`자가거주여부` 코드 의미** — 정의서는 "자가=1"인데 샘플은 전부 `3`. 무주택 판정에 직결.
- **`bizPrd` 마감의 의미** — 진짜 종료 vs 매년 반복사업의 올해 회차 종료 구분.
